追溯不到的，不写。

## 这份目录回答什么

「**当初为什么这么做？**」—— 尤其是「**否掉了哪些方案、为什么否**」。
只记结论不记否决理由的决策，等于没记。

`BACKLOG.md` 里那种以抱歉语气写的句子（「这个不该我顺手改，是产品决定」）承载的
其实是项目最重要的记忆，却被写成了最不重要的样子 —— 过三个月谁也搜不到。

---

## 一篇 ADR 要写什么

| 部分 | 要求 |
|---|---|
| 状态 | 提议中 / 已采纳 / 已废弃（被哪篇取代） |
| 日期 | ISO 日期。**没有日期的 ADR 等于没有** |
| **依据** | **追溯到最高指示第几条**（必填；写不出编号说明这篇不该存在） |
| 背景 | 当时的事实。只写事实，不写猜测 |
| 决定 | 一句话能说清的那句 |
| 被否决的方案 | **这一节是 ADR 的价值所在** |
| 后果 | 变好了什么、变糟了什么、欠下了什么 |

---

## 什么时候写

- 改了对外接口的语义（字段增删、状态码变化、默认值变化）
- 改变了安全边界
- 决定了「某块内核抄 goose 的哪一份 / 刻意不抄」这类方向
- **放弃了某个能跑但不对的实现**（这类最容易丢，也最容易被重新发明）

不写：日常实现选择、代码组织、bug 修复 —— 那些在 diff 与提交信息里。
