# ADR —— 架构决策记录

## 这份目录回答什么问题

「**当初为什么这么做？**」

`BACKLOG.md` 里那种以抱歉语气写的句子 ——「这个不该我顺手改，是产品决定」
—— 承载的其实是这个项目**最重要的记忆**，却被写成了最不重要的样子。
过三个月谁也搜不到、也读不懂当时否掉了哪些方案、为什么否。

所以凡是**改变了对外契约**的决策，都单独成篇。

## 一篇 ADR 要写什么

| 部分 | 要求 |
|---|---|
| 状态 | 提议中 / 已采纳 / 已废弃（被哪篇取代） |
| 日期 | ISO 日期。**没有日期的 ADR 等于没有** —— 半年后没人知道它是否还成立 |
| 背景 | 当时的事实。**只写事实，不写当时的猜测** |
| 决定 | 一句话能说清的那句 |
| 被否决的方案 | **这一节是 ADR 的价值所在。** 只记结论不记否决理由的决策，等于没记 |
| 后果 | 变好了什么、变糟了什么、欠下了什么 |

## 什么时候该写一篇

- 改了对外接口的语义（字段增删、状态码变化、默认值变化）
- 改变了「必须问你 / 我自己定」的分界
- 引入或放弃一条安全边界
- **放弃了某个能跑但不对的实现**（这类最容易丢，也最容易被人重新发明一遍）

不该写：日常的实现选择、代码组织、bug 修复 —— 那些在 diff 与提交信息里。
