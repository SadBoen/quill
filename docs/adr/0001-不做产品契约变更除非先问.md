# 0001 · 不做产品契约变更除非先问

- **状态**：已采纳
- **日期**：2026-10-07（确立于项目早期，写进 `WORKING.md` 的决策权限表）

## 背景

`WORKING.md` 把决策分成两列：「我自己定」与「必须问你」。技术选型、拆文件、
修 bug、补测试属于左边；**产品契约变更（对外接口语义变了）属于右边**。

这条分界的必要性，在 2026-10-07 撞到了具体场景：`GET /api/teams/{id}/dispatch`
是否应该按 `team_id` 过滤。台账的键是 `(owner, room_id, round)`，要让列表真的
按团队过滤，就得把 `team_id` 并进键里 —— 那会**改写已有台账**，且改变这个端点
的语义。开发者已经在同一轮里改了 POST 那条（只加校验、不动语义），很容易顺手
把 GET 也改了。

## 决定

改变**对外可观察行为**的改动，先问再做。「不改语义、只补校验」不算 ——
那属于修 bug，不属于契约变更。

## 被否决的方案

| 方案 | 为什么否决 |
|---|---|
| 顺手把 GET 也改成按 team_id 过滤 | 它改的是已存数据的键。别人的台账会读不出来，而这是个单人自用项目 —— 改键的收益（列表更准）远小于风险（历史派工记录读不出来） |
| 什么都不做，保持 `{id}` 被丢弃 | 那是在明知有歧义的前提下维持一个假接口。调用方无从知道自己问的是哪个团队 |
| 把 `{id}` 从路由里去掉 | 破坏了 URL 的自解释性，且是破坏性变更 |

## 后果

**变好了**：不会出现「开发者觉得顺手，用户的数据读不出来」。

**欠下的**：多一次来回。已付出的代价：B2-1 至今标着「两端都不再丢弃、但仍
不按团队过滤」，且台账键要改这件事被明确记在 `BACKLOG.md` 里等人决定。
