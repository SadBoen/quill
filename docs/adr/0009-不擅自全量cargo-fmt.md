# 0009 · 不擅自全量 cargo fmt：项目从未采用它

- **状态**：已采纳（**待用户拍板是否改变**）
- **日期**：2026-10-08

## 背景

用户要求「运行格式化」。以代码为准复核得到的事实：

- 仓库**没有** `rust-toolchain.toml`，也没有 `rustfmt.toml`。
- `.scripts/gates.sh` **不跑** `cargo fmt`。
- `.github/workflows/gates.yml:51` 注释原话：「这里刻意**不**开 clippy/rustfmt：
  它们要花时间装，而本工作流并没有跑它们」。
- 实测 `cargo fmt --all -- --check`：**481 个文件**有差异。

也就是说：**这个项目从来没有把 rustfmt 当格式化标准**，代码是人手排版的
（多为按阅读需要主动换行）。这不是回归，是一处**有意的空白**。

## 决定

**本轮不执行全量 `cargo fmt`。** 只保证**本轮改动的文件**格式自洽；
把「是否采用 rustfmt」作为**产品决定**留下来，交用户拍板。

## 被否决的方案

| 方案 | 为什么否决 |
|---|---|
| 直接 `cargo fmt --all` 提交 | 481 个文件的机械重排会把**本轮真正的改动**（迁移清单、判据修复）淹没在一个巨型 diff 里，review 不了。而且项目没有 fmt 门禁，重排完**立刻开始腐烂**（新代码不会被检查） |
| 重排 **+** 把 `cargo fmt --check` 加进 `gates.sh` | 「加门禁」按 `WORKING.md` 属可自决，但**格式化标准本身就是产品决定**。一次提交里同时定标准和执行全量重排，等于替用户决定了他没决定的事 |
| 什么都不做，也不说 | 用户明确要求过格式化。**不说就是隐瞒**，所以必须有这篇 ADR 与交付说明 |

## 若要采用，正确的做法（供拍板后执行）

1. 加 `rustfmt.toml`（若需要非默认风格）与 `rust-toolchain.toml`（钉住 rustfmt 版本，
   否则换台机器/升个版本就会重排出新差异）。
2. 单独一次提交：`cargo fmt --all`，提交信息写明「引入 rustfmt 标准」。
3. 同一批把 `cargo fmt --check` 接进 `.scripts/gates.sh` 与 CI —— **只重排不接线，
   等于让标准当场腐烂**。

## 后果

**变好了**：本轮的 diff 保持可读；没有替用户做产品决定。

**欠下的**：`cargo fmt --check` 现在仍会报 481 个文件。这是一处**公开的空白**，
不是「已格式化」。
